# Chromium 上游更新与安全补丁维护

本流程由用户于 2026-09-13 授权执行。目标是及时发现正式 Stable 和已被利用漏洞，准备可审核升级候选，并分别验证源码、构建产物与安装运行状态。

## 2026-10-05 授权更新：自动升级、提交与发布

用户已授权本任务在保持 Aegis 功能和安全行为不退化的前提下，自动适配正式 Chromium Stable、处理合并冲突、验证后提交并推送 GitHub、按仓库保护规则合入默认分支、创建产品版本 tag、使用既有发行身份签名及公证、发布正式 Release，并验证已有客户端的更新链路。此授权取代下文旧流程中“只准备候选”和“发布等待另行审核”的范围限制；仓库要求的必需检查和人工审核仍须满足。

每天北京时间 09:00 执行原任务 `aegis-chromium`，名称改为“Aegis 上游自动升级与发布”，保持启用，不重复创建任务。新授权不包含付费资源购买、新增预算、新签名身份、强制替换在用 App 或用户资料、绕过安全控制和向外部人员发消息。

执行顺序与验收：

1. 官方核查 → Mac ARM64、Windows x64、Android ARM64 分别核对公告、正式 Stable 和提交；保存来源、CVE、已利用状态、版本与时间。失败不算无更新，iOS 不套用 Chromium 结论。
2. 隔离适配 → 复用唯一候选目录，保护开发差异及并行任务，完整重放 Chromium/V8 补丁。语义冲突由任务解决，不删功能或跳过测试；每次真实 Mac 编译/打包递增产品版本。
3. 构建验收 → 冻结本次功能基线，核对上游安全回归、原生测试、权限与资料兼容、三平台实际产物和实机结果。旧测试、部分通过、模拟器和共享 V8 证据不能替代全部平台验收。
4. GitHub 提交 → 只提交升级相关文件，用配置的 SSH 身份推送，遵守默认分支保护；需要 PR 时自动创建并等待必需检查/审核后合并。核对远端提交与被测构建身份，不强推或混入无关改动。
5. 正式发布 → 独立核验 Release API 权限、正式签名和公证条件；先上传全部必需平台资产到草稿，核对版本、命名、大小、摘要及签名，再公开正式 Release。保留 Android 包名、发行签名及递增 versionCode；不覆盖旧 tag 或历史包。
6. 更新验收 → 旧版客户端真实发现公开新版本、下载并校验，在隔离测试资料上安装并回读版本与功能，再确认新版本仍可检查更新。缺包、损坏包、网络失败、降级拒绝与恢复路径同样验证。

当前桌面更新能力是关于页检查正式 Release、自动下载和校验、用户手动安装；不是静默安装。Android 更新入口单独核查并补齐，不能假定桌面实现自动覆盖 Android。更新协议变更必须兼容旧客户端，必要时提供桥接版本。

现有候选工作流尚不含正式发布步骤；任务需补齐并验证编排，不能把修改任务配置视为流水线已接通。缺少构建机、测试设备、既有签名凭据、发布权限或必需审核时，先完成可独立推进的工作，再报告具体缺项，保留现场并保持定时检查启用。正式发布与客户端安装回读完成前，不报告整条链路完成。

下文保留原监控设计和历史记录；涉及旧授权范围的描述以本节为准。

## 开发前基线核验与源码同步

每次开发先获取真实 GitHub 默认分支和官方正式 Stable，分别记录产品仓库提交、桌面及 Android pin、补丁数量和完整重放结果、实际 Chromium/V8 源码提交。`apps/browser/.chromium-root` 只定位构建目录，不能证明产品主线已经升级；本地同名 `origin/main` 也必须核对远端 URL。排除 Early Stable。当前目录为旧提交、存在未提交改动或并行写入者时，保留现场，在最新远端主线的独立工作树中整合，禁止强制切换或混入无关差异。

升级进度分开记录，不得只保留“候选进行中”：

1. **源码同步**：已完成的 pin、补丁、适配、流程代码及验证记录及时提交到升级分支并创建草稿 PR。构建机、签名或发布 API 凭据不足，不阻止这一步。未完成的平台验证在 PR 中明确标出。
2. **主线合入**：源码审核和必需 CI 通过，并满足既定功能与平台兼容门槛后再合入；草稿 PR 或 Mac 局部通过不等于主线已升级。发布凭据与源码兼容验证分别列出，不相互替代。
3. **正式发行**：三平台实际产物、既有发行签名、完整发布与旧客户端更新验收满足后，才创建正式发行结论。不得降低门槛、编造收据或将不完整版本标为 latest。

开发可以继续使用已核对的最新上游整合分支；报告必须同时写清远端 main 和开发分支的版本差异。新增功能加入 `apps/browser/release-feature-contract.json`，补上真实回归入口，并在下一轮上游适配中保留。源码整合分支与唯一 Chromium 构建树分开管理，后续提交以远端最新主线及已审核升级提交为准，不能用旧隔离产品目录覆盖新改动。

本次排查见 [2026-10-08 源码同步记录](audit/upstream-source-sync-2026-10-08.zh-CN.md)。

## 调度与来源

- 在当前 Codex 任务中每天北京时间 09:00 运行一次检查，GitHub 在 09:17 补充核查。普通更新最多每日汇总；已被利用漏洞、新的采集失败、恢复、候选失败或需要处理的变化立即报告。已报告的相同状态保持安静。
- 本地计划任务需要电脑开机、Codex 应用运行、项目可访问；这不是独立服务器上的全天候监控。
- 官方来源：Chrome Releases 的 JSON 公告流、ChromiumDash 的平台 Stable 记录、VersionHistory 的平台版本，以及 chromium.googlesource.com 的发布标签。
- 固定回查最近 45 天。已记录但未覆盖的已利用漏洞持续保留，不因超出回查窗口消失。首次运行不能保证覆盖 45 天以前的所有历史漏洞。
- 排除 Early Stable 和小比例提前投放；不能把最大版本号直接作为正式 Stable。Mac ARM64、Windows x64、Android 分别核对；iOS 的 WebKit 更新另行跟随 Apple，不套用 Chromium 版本结论。
- 公告、API、标签不一致或获取失败时，结果为不完整，保留上次成功时间；不能报告“没有更新”。标签与 ChromiumDash 的源码提交必须一致。
- 同一轮中，相同版本的已验证源码标签只读取一次，Mac、Windows 仍分别核对各自公告、版本历史和提交。标签主路径出现网络错误时，使用同一官方仓库的版本别名路径，记录实际来源与原错误；提交不符或内容损坏不以备用结果掩盖。两条路径均失败时仍报告不完整，不跨轮使用缓存冒充新检查。

## 执行与证据

在项目根目录执行：

```bash
python3 apps/browser/scripts/check-chromium-upstream_test.py
python3 apps/browser/scripts/check-chromium-upstream.py
```

脚本只读正式版本、源码位置和本机 App 包元数据，只在 `.artifacts/chromium-upstream/monitor/` 写入结果：

- `latest.json`：最新核查、来源 URL/内容摘要、平台候选、未解决的已利用漏洞、检查错误。
- `last-success.json`：最近一次完整成功核查；失败运行不会覆盖。
- `state.json`：上次尝试与成功时间、报告去重指纹。
- `runs/`：状态变化时保存的历史证据，不重复保存同一状态。
- `check.lock`：排斥同时运行的检查。退出码 0 表示检查完成，2 表示结果不完整；两者都不表示安全更新已经安装。

`notification.notify` 是本轮报告建议，不是消息已送达的证明。定时执行器还要检查运行记录与当前任务上次实际报告，避免中断时漏报。普通待报变化会保留到每日汇总窗口。包元数据不证明签名、源码回补或正在运行的进程；旧安装包仍在时不能因为修改了源码版本就解除提醒。

## 候选流程与验收

1. 发现 → 核对平台正式公告、版本与提交，并保存候选版本。每天检查，不承诺 1 小时内发现；发现后响应目标：已被利用漏洞 24 小时候选验证，普通安全更新 72 小时验证。这是目标，超期必须报告原因。
2. 保存现场 → 记录主仓库、Mac 源码、V8 的 HEAD、补丁差异和未跟踪源码；不覆盖、清理或丢弃开发改动。
3. 隔离准备 → 统一使用 `${LOCAL_WORKSPACE_ROOT}/GCSA-aegis-build/upstream-candidate`，复用共享 Git 对象；每次只有一个候选在执行。读取当前候选记录，已有任务运行时不重复拉取/构建。版本变更先保存旧候选证据。
4. 重放 → 在候选的独立源码和 V8 中按序应用所有项目补丁，核对依赖版本。遇到冲突保留 Git 状态、补丁编号和错误，由当前任务进行有依据的适配；禁止无条件采用 ours/theirs 或跳过补丁。
5. 测试 → 先验证受影响源码和补丁，再运行相关上游回归、Aegis 原生测试、构建与真实 App 验收。每次 Mac 编译或打包前递增产品版本/构建号，并保持后续候选构建路径一致。
6. 审核 → 完成版本双 pin、补丁、依赖、构建身份、测试报告和升级/回退说明后形成候选。源码修复、产物构建、设备安装运行分别记录，不能相互替代。
7. 发布 → 合并、正式签名/公证、替换固定验收 App、发布与终端自动升级，等候候选结果审核；监控任务不自行执行。

当前正式源码入口是产品主仓库的 main。隔离候选只用于准备与检查，不把主仓库版本文件先改成尚未通过的版本。禁止在已有开发工作区直接运行可能 `checkout --force` 的旧 fetch 脚本。空间不足时保留候选和准确失败原因，不自动删除 out、源码、依赖、用户资料或旧证据。
