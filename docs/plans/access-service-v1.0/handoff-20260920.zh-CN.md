## 现有构建的所有权与后续动作

当前 `-j4` 构建由原验证任务所有。接手人先向所有者取得完成日志、目标和过滤条件，再按其约定在**原隔离工作区**读取结果；不要 reset、清理、重放补丁、改 GN args、启动第二个并发构建或终止进程。若尚未结束，只登记 BUILDING，不写 PASS/FAIL。失败时保留第一处真实失败及工具链/源码归因；成功时进一步记录测试二进制与每个执行过滤器的退出码，不自行扩大结论。

下一代码单元按[开发计划](development-plan.zh-CN.md)的顺序推进。交接给实现和审查者的最小清单：

1. 在新任务中刷新 `origin/develop` 和 upstream 精确 SHA，选隔离 worktree；记录 base、head、源码树、补丁集合、Chromium 基线、GN args 与所属构建任务。先复核 `CommitIdentity` / `CommitSelection` / `PublishCommittedPolicySnapshot` 的生产调用空白。
2. 为最小 coordinator 写清可信 host → 普通网站协议组选择（DEV/Alpha 调试三策略独立协调）→ identity/selection/base-proxy 代次 → commit/persist/recover → snapshot publish → dispatch/cancel ACK → UI 的接口和版本关系；将 timeout、cancel、restart、signed-out、保存失败及无 DIRECT fallback 列为同单元回归。对应 P1/P2/P4/P5 的局部合同不能伪装成 P0/G1 完成。
3. 以真实 Profile/StoragePartition 和受控 HTTP fixture 执行正常与失败路径；随后接 Xray→REALITY 和托管身份/租约，逐层补服务端计量与限额，再扩展请求矩阵和四渠道 UI。每个新入口列测试名、实际运行结果、未覆盖范围。
4. 独立 Review 检查最终 HEAD 的完整实现、overlay/顺序补丁/BUILD 接线、冻结语义、失败回退和测试；按[DEV CI 指南](../../development/ci.zh-CN.md)核对本地最终 HEAD、PR B/H/M、最新 attempt 及合并后 S。旧 run、旧 review 和本交接快照不能代替新候选证据。
