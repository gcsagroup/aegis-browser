冻结事务顺序为：验证可信 selector 与 store → PREPARED journal 预留 operationSequence → 从旧 durable base 构造完整候选 → 发布到浏览器 request runtime → 向所属 NetworkContext 发布精确 operation/G/S/E 与 owner/partition → 全部候选 ACK → 再原子 durable commit → finalize。PREPARED 的 `committed_policy_generation` 始终为 0，候选及成功提交的 policy generation 都等于预留的 operationSequence。请求路由只读取内存快照，不读取 SQLite。`RepublishCurrentConfigWithAck` 不能作为候选发布证据。

Profile 持有首个可信 store（含 ephemeral 会话库），后续 mutation 传空指针复用，禁止替换库。候选保留无关网站组和独立规则。当前 transport 只有 partition/host 粒度：同 host 的其他规则需要相反 DIRECT/PROXY 策略时，发布前返回 `kUnsupportedTransportScope`，保留原状态；不宣称已实现按 top-level-site 区分的 transport。浏览器同步重绑定保留端点的 policy generation，并在 DIRECT 时从 CustomProxyConfig 的 exact-host 列表移除目标网站、保留其他网站；候选 config 与 metadata 使用同一 Mojo channel 顺序发送。失败仅在候选仍精确匹配时恢复旧快照/端点，并 supersede journal；清理写入失败透传 store 错误并保留待恢复边界。提交前重新核对 runtime、权威 selection source 的 S/E、完整端点及所有 NetworkContext 的集合；新 context、版本变化、错误或丢失 ACK、30 秒超时均阻止提交。迟到 ACK 不能复活已取消的事务；失败的 exact identity 释放 tracker 容量。Network Service 在受信任的 context channel 上保存 owner 绑定、单调的候选回执；它不从数据库重建策略。BLOCK/ALLOW 的屏障及取消流程、可信 UI 入口、真实身份/节点提交与 Xray 集成不属于此阶段。

CI 去重和分类优化另立 PR，先保持当前 full 门；用必需层故障 fixture 验证新汇总后才调整保护条件。纯文档将来可轻量化，当前没有豁免。优化失败走可审查 revert，保留原 full 路径与证据。每个候选分别记录 B/H/M/S、产物 digest、run/attempt、过滤器、匹配数与首个失败日志；flake 不用重复运行掩盖，必需安全测试不得靠隔离移出门禁后变绿。普通功能锁定版本，上游最新兼容性单独监测。分支与审查治理沿用[DEV CI 指南](../../development/ci.zh-CN.md)，不从本交接推断合并或发布许可。

下一代码单元按[开发计划](development-plan.zh-CN.md)的顺序推进。交接给实现和审查者的最小清单：

1. 在新任务中刷新 `origin/develop` 和 upstream 精确 SHA，选隔离 worktree；记录 base、head、源码树、补丁集合、Chromium 基线、GN args 与所属构建任务。先按上表关闭**当前**固定 Chromium 编译/运行欠账，不能以计划中的窄 prefetch filter 代替全部入口回归；现有失败需先定位和修复。同步复核 `CommitIdentity` / `CommitSelection` / `PublishCommittedPolicySnapshot` 的生产调用空白。
2. 为最小 coordinator 写清可信 host → 普通网站协议组选择（DEV/Alpha 调试三策略独立协调）→ identity/selection/base-proxy 代次 → PREPARED → candidate snapshot publish → execution ACK → durable commit/recover → UI 的接口和版本关系；将 timeout、cancel、restart、signed-out、保存失败及无 DIRECT fallback 列为同单元回归。对应 P1/P2/P4/P5 的局部合同不能伪装成 P0/G1 完成。
3. 以真实 Profile/StoragePartition 和受控 HTTP fixture 执行正常与失败路径；随后接 Xray→REALITY 和托管身份/租约，逐层补服务端计量与限额，再扩展请求矩阵和四渠道 UI。每个新入口列测试名、实际运行结果、未覆盖范围；A01–A118、PF01–PF13 的实现/映射/执行/结果/覆盖分开写入[追踪表](acceptance-tracker.zh-CN.md)。
4. 独立 Review 检查最终 HEAD 的完整实现、overlay/顺序补丁/BUILD 接线、冻结语义、失败回退和测试；按[DEV CI 指南](../../development/ci.zh-CN.md)核对本地最终 HEAD、PR B/H/M、最新 attempt 及合并后 S。旧 run、旧 review 和本交接快照不能代替新候选证据。
5. 每完成一个阶段，在该阶段 PR 内同步更新本开发计划与 Handoff，再让独立 PRO reviewer 对最终 HEAD 复审。依赖上一阶段代码的后续阶段，等上一 PR 实际合并且最新 `develop` push CI 成功后，从该最新 `develop` 新建隔离分支；等待期间只进行只读准备。

```bash
git show -s --format='%H %T %P %s' HEAD

gh pr view 133 --repo quinn521/aegis-browser --json state,headRefOid,baseRefOid,mergeable,statusCheckRollup

```
