## 若保持 $40 上限，下一阶段的步骤与验收

1. **先做不付费的目标裁剪评估 → 对比 GN 依赖图。** 保留完整 chrome、mini_installer 和全部 aegis_browser_unittests；评估为同一份 EnhancementBrowserTest 当前七项测试建立专用浏览器测试程序，复用原 fixture 和运行支持，避免为了七项测试编译整个 Chromium browser_tests。仅加运行时 gtest_filter 不会减少编译量。此项需要代码与依赖验证，目前尚未实施。
2. **先验证修复与测试等价性 → 标准 Windows 门禁。** 在可用的免费入口验证异常保留、SDK 和工具链；专用测试目标必须确实包含原四项测试及 Ver 5.0 (207) 新增的三项 Markdown 首次打开回归，不能删除用例或将模拟测试冒充原生测试。免费机器的存储和时限不适合直接承担完整 Chromium 构建。
3. **额度恢复且用户另行授权后再考虑试跑 → 预算和源码双重核对。** 以 main 的明确提交冻结源码；现有 runner 组曾限定旧集成分支，重新执行前需核对并迁移到 main 的同一工作流。不能扩大仓库或工作流授权范围。确认组织其他任务也不会争用剩余额度。
4. **给编译、原生测试和上传分别留时间 → 检查实际阶段预算。** 目标总计 225 分钟、约 $36.45，余下金额作共享用量及存储余量。能否达到该目标必须根据目标裁剪和实际耗时再评估；证据不足时不启动付费构建。不得仅把内部 210 分钟改大，期待最后恰好赶上预算。
5. **完整编译和测试通过才交付 → 核对 JSON 与安装包。** 两组测试均不得重试掩盖失败；若又超时或失败，保留原始异常和附注、下载全部日志，不自动重跑。安装包、交互验收、签名和发布分别记录。

若无法有效减少编译范围，而又没有可用的自有 Windows 环境，就需要调整预算或交付时点；当前约束下不能承诺免费完成剩余完整编译。
