# GCSA Aegis 增强与整合方案

评估日期：2026-09-14。范围：当前主仓库、固定 macOS 验收 App、近期论文与作者项目。本文是实施建议，不表示新增功能已实现或研究指标已复现。

**建议把下一阶段定位为“可信、可核验的隐私浏览助手”：先完成内核安全升级，再强化 Agent 数据边界和结果核验，随后把研究、收藏、下载与监控整合为一个工作台。** 第一方追踪识别和本地钓鱼模型适合小范围实验；WebGPU 深层防护、自学习 Agent 和通用恶意脚本阻断放在后面。

## 1. 目标、假设与完成标准

- 产品方向沿用本地优先、隐私与安全浏览器；近期以 macOS 为主，Windows/Android 单独安排实际设备验收，iOS 保持独立产品边界。
- 复用现有 Chromium 原生 Agent，不替换为另一套拥有通用 CDP 或脚本权限的外部自动化框架。
- 本轮只做评估与方案，不变更浏览器实现、设置、模型、发布状态或现有上游升级任务。
- 完成标准：核对现有能力与不足；搜索并打开论文原始来源；给出可集成位置、收益、代价、先后依赖和验收要求；执行现有相关测试并说明证据范围。

步骤与验证：源码盘点 → 阅读真实入口及测试；论文筛选 → 核对日期、方法和作者代码；方案排序 → 明确依赖与退出标准；交付复核 → 运行 Core 测试、仓库合同检查和文档链接检查。

## 3. 近期论文筛选及集成判断

检索覆盖 arXiv、USENIX、OpenReview 和作者 GitHub。下列依据采用论文原始页面、会议页面或作者仓库；搜索聚合页仅用于发现线索。时间截至 2026-09-14，不宣称穷尽所有新论文。预印本、论文自述录用和正式会议页面分别标明。

### A. WebMCP-Phalanx：先补原生约束，再考虑模型审查

**2026-08-25，arXiv 预印本。** 研究将工具归属与生命周期约束放在浏览器侧，并让无工具权限的模型检查不可信材料。论文仍报告工具返回内容攻击成功，以及恶意工具名在审查前触发调用的绕过，不能理解成彻底解决提示词注入。[论文](https://arxiv.org/abs/2608.24017) · [全文](https://arxiv.org/html/2608.24017v1)

**适合 Aegis 的增量：** 在现有 Broker/Actor 中绑定工具来源、文档版本、权限及撤销状态；在工具进入模型上下文和调用前检查完整元数据；网页工具的“只读”自述不产生只读权限。先做确定性限制，语义审查作为附加风险信号，不能独立放行动作。本轮未核实可直接复用的作者实现，按方法重做小实验，成本中高。

WebMCP 本身已在 Chrome 官方文档列为 origin trial，文档更新于 2026-08-07。Aegis 已有 list/invoke 入口，下一步是受控接通少量合作站点，不是增加一个入口后全面开放。[官方文档](https://developer.chrome.com/docs/ai/webmcp)

### B. MINIM：从“删掉敏感词”进到“只给当前任务需要的内容”

**2026-06-11，论文页面标注 ICML 2026 接收。** 方法在本地分别评估界面元素的敏感性与任务必要性，再选择保留、抽象或移除。[论文](https://arxiv.org/abs/2606.13949)

**建议优先实验。** 接在页面观察到模型请求之间，复用现有脱敏；先实现选区、指定页面和任务字段白名单，再比较学习式裁剪是否有额外收益。用于总结文章时，不发送旁边账号菜单、无关通知及其他标签页内容。截图必须走独立裁剪/遮挡路径，文字已脱敏不表示截图安全。

[作者代码](https://github.com/yyyyhx/MINIM)可访问，但本轮未从仓库页面确认完整代码、权重与数据的复用许可组合；导入前单独核验。第一版可只实现方法启发的规则裁剪，不依赖研究权重。成本中等。

### C. Monitoring Web Agents Without Internal Signals：提前发现任务走偏

**2026-09-02，预印本。** 利用可观察动作、环境反馈及意图一致性预测任务是否趋向失败，不要求模型内部 logits；论文在固定误中止预算下讨论提前干预。[论文](https://arxiv.org/abs/2609.02057)

**建议先做轻量版。** 在现有执行循环增加连续无进展、同一错误重复、关键页面丢失和目标字段缺失的检测。触发后重新观察、有限重试或请求接管。学习式预测器先只记录，不直接中断用户任务；待误中止率可接受后再启用。论文页面未确认现成部署包，不能估成即插即用。成本低至中等。

### D. SCAFFOLD：把已验证的成功过程变成可复用步骤

**arXiv 页面标注 2026-08-31 提交、EMNLP 2026 接收；作者仓库仍保留 submission 文案。** 研究从多条成功轨迹抽象、组合和压缩技能，并包括向模型权重蒸馏的训练环节。发表状态以作者页面说明为限。[论文](https://arxiv.org/abs/2609.05511)

**适合后期的有限借鉴：** 为高频站点保存经过验证的检索/筛选步骤，带适用来源、页面版本、过期时间和撤销入口。每次执行仍经过现有 Broker，技能不能保存密码、扩大授权或跳过确认。作者[仓库](https://github.com/BokwaiHo/SCAFFOLD)写明 Apache 2.0，并要求另装真实评测环境；本轮没有复现完整训练。暂不做自动训练、自改策略和全量浏览历史记忆。成本中高。

### E. SST-Guard：加强第一方中转追踪识别

**2026-04-30，arXiv 预印本。** 从网络、Cookie、window 对象中的语义模式识别 server-side Google Analytics，覆盖范围是该类收集路径，不能泛化为所有服务端追踪。[论文](https://arxiv.org/abs/2604.27497)

**建议作为隐私差异化实验。** 复用已有网络与第一方收集信号，离线生成小规则集，在客户端观察“标识符类别、事件类别和目的地关系”，不保存原始标识符。先只观察，人工标注常见中文站点、登录、支付和统计用途，验证后逐站启用。请求体深度检查应有资源上限且不进入同步加载热路径；混合业务/统计端点不能粗暴全拦。成本中高。

### F. WGPULens 与 Double-Edged Shield：指纹保护要测隔离，也要测独特性

**WGPULens：2026-06-24，预印本。** 研究显示部分 pipeline 编译状态可跨特定边界观察，静态 adapter 字符串降熵不足以覆盖这些通道。[论文](https://arxiv.org/abs/2606.26412)

**Double-Edged Shield：USENIX Security 2025 正式会议论文，作为补充基础。** 研究指出个性化广告过滤列表可能增加用户可识别性。[会议原文](https://www.usenix.org/conference/usenixsecurity25/presentation/el-hajj-chehade)

**建议：** 先补普通/无痕、跨站、跨 Profile 的隔离测量；默认提供少量经过兼容性验证的保护预设，不鼓励任意拼装大量过滤规则。GPU 缓存修改应结合 Dawn/Chromium 上游，单独做性能与兼容性原型，不能先改驱动级缓存后再找收益。成本高，排在 Agent 与升级之后。

### G. OctoWatch：让“安全下载”重视仓库与发布者证据

**2026-08，USENIX Security 2026 正式会议论文，题为 Beyond the Stars。** 研究融合仓库文本、用户与仓库关系、时间活动等信息检测恶意仓库，指出真实基率及标签偏差会让离线高分失真。[会议原文](https://www.usenix.org/conference/usenixsecurity26/presentation/galloway)

**适合借鉴，暂不照搬模型。** 安全下载卡片并列展示官网到仓库的关联、实际发布者、版本、摘要和签名状态；GitHub 域名、星数、下载量只作上下文。全文描述的是需要大规模数据支撑的系统，本轮未确认可直接消费的模型或情报服务。先做确定性来源证据，之后再评估离线信誉模型。成本低至中等，完整模型则高。

### H. MUZZLE 与 WebArena-Verified：先整合评测，再扩大权限

**MUZZLE：2026-02-09 首稿，2026-06-14 修订。** 从实际轨迹选择注入位置并适应性调整攻击，适合测试静态样例覆盖不到的失败模式。[论文](https://arxiv.org/abs/2602.09222)

**WebArena-Verified：2025 年工作，2026 年持续提供工程接入。** 作者项目采用审计后的任务与确定性评分，提供网络轨迹离线重放；这是验证基础设施，不是产品执行器。[作者项目](https://github.com/ServiceNow/webarena-verified)

**建议最早整合。** 从其评测方法出发建立 Aegis 原生工具适配器，先做可重复的 30 个任务和 100 个隔离注入场景，使用合成秘密和本地测试站点，不攻击第三方或暴露真实账号。优先复用现有环境；如必须增加容器，评测阶段使用一个可复用环境，不按测试用例反复创建镜像和卷。完整官方 benchmark 如需多服务拓扑，另行记录成本，不能把小样本分数当成官方榜单结果。

### I. 本地钓鱼模型：成熟基线比单纯追新更有价值

**PhishLang：2024 年首稿，2025-04-16 修订。** 以 MobileBERT 做端侧网页语义检测，适合作为轻量模型对照；它不是今年新论文，也不是当前 Aegis 已复现的能力。[论文](https://arxiv.org/abs/2408.05667)

建议比较“当前规则”“规则加轻量文本模型”“规则加按需视觉”三组。现有代码已经识别 OTP/seed phrase 等文本词，不应重复记为完全缺失；需要补的是结构化输入意图、提交时检查和场景覆盖。模型只看灰区，超时或不确定时弃权。第一轮不将模型分数直接变成硬拦截。

## 4. 产品整合：形成三个用户能直接理解的入口

### 4.1 页面保护

复用现有盾牌，展示“拦了什么、依据是什么、对当前页面有什么影响”。合并跟踪请求、Cookie、链接、指纹信号、钓鱼和下载来源信息，按事件去重，不用总分代替实际证据。

保留单站临时例外、恢复默认及影响说明。用户说“登录失败”时，先定位相关事件，再给出最小调整预览。论文启发的“疑似”必须和确定命中区分；不因模型解释语气肯定就增加拦截权。

### 4.2 研究工作台

把现有摘要、研究、标签组、收藏和监控串成流程：选择页面 → 提取带来源的事实 → 多页比较 → 保存结果 → 订阅后续变化。

第一版只支持用户选择的 3–10 个网页，输出含日期和来源的比较结果；事实和模型推断分开，引用点击能回到原文位置。监控复用已有变化摘要，不新建调度器。之后再接只读论文元数据连接器，例如 arXiv/OpenAlex/Zotero；这些是后续候选，本轮未评估其接口、速率或许可，不计入已核实可直接接入项。

历史语义搜索采用用户主动加入的项目资料，提供可查看、可删除、可到期的本地索引。普通/无痕数据保持隔离；不默认索引所有历史、登录页或私人表单。

### 4.3 下载与任务中心

把官方下载发现、来源核验、实际下载和后续版本监控连接起来。卡片分开显示“来源有依据”“摘要一致”“签名已核验”“已安装版本”，不把下载成功显示为安全保证或升级完成。

任务中心复用现有时间线及任务存储，增加可展开的结果证据、停止原因和恢复入口。对跨站写入呈现接收方与发送内容；后台页面内容不能自己成为用户批准。

## 5. 实现结构：只扩展现有边界

1. **观察层：** 在现有 PageSnapshot/Actor 观察中保留来源与文档身份，增加按任务裁剪的视图；不要直接改成采集更多数据。
2. **策略层：** 扩展 `AgentPolicyBroker` 的来源、数据类别、目的地和生命周期检查。先采用保守的上下文隔离；自由文本经模型改写后不能假装实现精确污点跟踪。
3. **核验层：** 扩展 `AgentResultVerifier`。页面有新观察只证明动作后的状态可见；业务目标另用结果字段、来源及目标条件核验。失败预测仅辅助决定重新观察，不替代确定性结果。
4. **呈现层：** 复用侧栏、保护气泡和任务时间线。不要再增加独立聊天页或第二套设置。
5. **更新层：** 在现有更新器之上评估签名元数据、过期与降级防护。可借鉴成熟的 TUF 设计，先比较现有平台更新组件能覆盖多少；完整 TUF 不是第一版必选依赖。[TUF 官方规范](https://theupdateframework.github.io/specification/)

## 6. 落地顺序与工作量

以下是“2 名熟悉 Chromium 的工程师、测试投入约半人”的规划估算，不是交付承诺。默认在既有工作上推进；内核冲突、模型实验或平台设备问题可能延长。阶段可以有限重叠，macOS 首轮约 8–12 周；单人执行应按工作量重新排期。

| 阶段 | 建议投入时间 | 可交付结果 | 退出标准 |
|---|---|---|---|
| P0：内核与发布基础 | 1–2 周，优先最高 | 完成已有升级候选；统一当前源码、测试和固定 App 身份；明确待修漏洞与更新状态 | 关键修复逐项有证据；同一产物通过原生、安装、重启回读及恢复验证 |
| P1：Agent 可信性 | 2–3 周 | 最小观察视图、目的地约束、失败恢复、任务结果检查及首批评测 | 冻结场景中无未经授权的敏感出站；任务成功率不因裁剪明显下降 |
| P2：整合体验 | 3–4 周 | 三入口串联；多页面研究、引用、保存、变化跟踪和下载来源卡片 | 用户能独立完成研究、保存、监控、查看变更及取消流程 |
| P3：隐私与检测实验 | 2–3 周 | 第一方追踪观察、灰区钓鱼模型、指纹隔离测量报告 | 独立数据证明增量收益、误报和资源开销可接受，再决定默认启用 |
| 后续研究 | 单独立项 | WebMCP 合作站点、自学习步骤、GPU 深层缓存隔离 | 前阶段边界已稳定，且每项有明确可复现收益 |

主线研发不等待所有研究实验成功。首轮交付不包括自动购买、通用网页工具开放、全量浏览历史训练或通用恶意 JS 阻断。

多项功能合并为正式特性版本时可按现有约定规划 Ver 2.0；仅修复阶段沿用现有构建号递增。每次真实 macOS 编译/打包更新版本，固定 App、签名身份和 Profile 不变。

## 7. 建议验收指标

这些是待基线校准的目标，不是本轮测量结果。实验必须冻结模型、设备、页面、规则与数据版本；训练/调参、测试按时间、注册域和活动模板隔离，不能让同一钓鱼模板同时进入训练与测试。

| 项目 | 建议门槛与验证办法 |
|---|---|
| Agent 基础任务 | 先固定 30 个任务，每个独立运行 3 次；报告单次成功率、3 次均成功比例、耗时及每个成功任务的模型用量；首轮目标成功率 ≥90% |
| 隐私裁剪 | 在相同任务与模型下，目标输入量下降 ≥30%，成功率下降不超过 2 个百分点；扩大样本并报告置信区间后才据此启用 |
| 授权边界 | 首批 100 个本地注入场景和生命周期场景中，合成秘密未经批准出站次数为 0；另做适应性攻击和漏报复盘，不能以 100 次零失败宣称普遍安全 |
| 结果核验 | 空点击、延迟跳转、目标未出现、旧文档、重复提交及下载未落盘场景不得报告目标完成；不是只检查工具返回成功 |
| 反钓鱼 | 独立良性集至少 10,000 页，含中文登录/支付/SSO；先设硬拦误报 ≤0.1% 的目标并报告置信上界、每万次误拦与召回；样本不足不升级默认拦截 |
| 第一方追踪 | 初期观察 200 个代表站点，至少 50 个含登录、支付、视频或文档操作；关键任务不得因新增规则失败，逐项分析混合用途端点 |
| 性能 | 在固定 Mac 及实际 Android 设备分别测量；常规页面导航额外开销目标 P95 ≤10ms，空闲 CPU 增量目标 ≤1 个百分点；模型分析异步且不阻塞加载 |
| 数据生命周期 | 导航、关闭无痕、暂停任务、用户接管、重启、取消监控后，旧授权/文档/敏感缓存按设计失效；核对磁盘、日志及出站，而非只看 UI |
| 更新交付 | 核验下载、摘要、签名、安装、重启版本、配置迁移与失败恢复；不能把 SHA-256 相同等同于可信发布者或安装成功 |

100 个安全样例、30 个任务、200 个站点属于工程起步规模，不构成广泛真实世界效果声明。Windows、Android 和 iOS 的通过状态分别记录。
