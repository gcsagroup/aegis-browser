# Aegis Browser Agent v2 架构与原型决策

## 决策

Browser Agent v2 停止继续扩展 v1 执行路径。保留 Profile 隔离、策略代理、固定原生工具、
审批、审计以及隐私/反钓鱼资产，重新实现由浏览器掌控的规划与执行循环。最终选择
**P4 原生混合方案**：模型负责理解和提出操作，Chromium 负责限定范围、执行、观察和验证。

当前开发基线是 Chromium 提交
`383d157c6f3601101038aef6ff964e61b6af7b4f`（tree
`2c509e07ec25fa8811adae17f9826e967c9bcee1`），由 106 个顶层补丁和 2 个嵌套 V8
补丁重建。当前还包含未提交增量；这个提交不能单独标识某个最新安装包，也不等于已经达到
公开发行资格。唯一开发入口及候选清单见[工作区说明](../WORKSPACES.zh-CN.md)。

## 当前开发增量的身份边界

44 文件候选及 `monitor-registration-candidate-r1` 已成为历史记录。当前 macOS 测试包
来自冻结的 49 文件 `goal-constraints-candidate-r1`，465 项原生回归全部单次通过；
本地 Qwen 使用原始完整限制语句成功注册监控，重启后保持监控及计划时间。主目录与
Android 构建区也已同步这份源码，但 Android 仍缺少对应的新包和实机验收。
本轮五个文件增量修复了否定句误判、重启状态提示和窄侧栏布局；不再在旧集成目录开发。
原生回归、本地可见界面、系统通知和三端发行证据分别记录，不能互相替代。

现有网页变化 AI 摘要比较两次浏览器核验的只读观察，
只发送发生变化的片段给原任务绑定的模型，仅暴露 `agent.summarize_monitor` 返回工具。
该工具不授予网页操作权限；摘要引用必须来自本轮变化，输出与当前内容摘要绑定，失败
不覆盖旧基线。单次最多两次模型请求，并计入原任务模型及网络预算；暂停、删除、关闭
Agent 或用户接管会沿现有检查生命周期取消请求，迟到结果按请求身份丢弃。

摘要与引用写入原有系统加密观察记录，不新增明文正文列；UI 以文本显示摘要及截断范围，
锁屏通知不包含摘要正文。数据库升级为 v8，明确阻止不认识新状态的旧程序读取/覆写，
从 v5、v6、v7 迁移均保留旧密文与调度状态。引用存在校验不能证明模型语义绝不幻觉，
仍需真实模型、异步浏览器、加密恢复及最终界面的分层验收。此增量尚非安装包交付结果。

## 产品目标

普通用户只需描述想要的结果，不应先打开正确网页、选择工作流或学习浏览器自动化。
Aegis 必须：

1. 理解目标和用户点名的网站；
2. 决定使用当前页、直接 URL、站内搜索还是纯浏览器数据；
3. 生成用户可见、范围明确的计划；
4. 每次只执行一个浏览器批准的工具；
5. 观察真实浏览器状态，必要时重新规划；
6. 只报告已经由浏览器验证的结果。

模型永远不会获得浏览器通用权限，也不能自行宣布任务成功。

## Runtime 流程

```text
桌面侧栏 / Android Agent 界面
  -> 目标路由（原生 agent.route_goal 函数）
  -> 浏览器目标解析与 scope 构建
  -> Planner（原生 agent.submit_plan 函数）
  -> PolicyBroker（工具、origin、tab、数据、预算、风险）
  -> 浏览器原生工具或绑定文档的 Actor 动作
  -> 观察与后置条件验证
  -> 下一次模型调用、用户接管或验证完成
  -> TaskStore、时间线和易懂结果
```

### 目标路由

第一次模型调用把目标理解为研究、浏览器管家、安全下载或购物，并提出入口类型。Chromium
随后应用确定性约束：

- 明确 URL 保持为 HTTPS 目标；
- 京东、Amazon、GitHub、YouTube 等点名网站使用该站自己的 HTTPS 首页或搜索 URL，
  不退化到通用搜索引擎；
- “当前页/这个页面”绑定活动的公开网页文档；
- 收藏夹、标签页等纯浏览器任务不会打开搜索页；
- 发现和对比默认是只读研究，只有用户明确要求购买操作时才进入购物权限。

### 规划与执行

Planner 只接收目标、已解析目标、数据类别、预算，以及浏览器已经批准的工具。它必须返回
一个严格的原生 `agent.submit_plan` 调用。每轮执行只能调用已注册工具，并且 schema、
风险、tab、origin、DocumentToken 和预算必须全部通过策略检查。每次动作后，Runtime
把有界结果交回模型；导航或用户接管后必须重新观察。

### 格式恢复

本地或云模型可能生成内容基本正确、但函数参数格式不合格的结果。v2 允许一次由浏览器生成
的修复调用，其中只包含被拒绝的 schema 错误。修复只能改格式，不能扩大工具、origin、
数据、风险或预算。如果两次规划都失败，Chromium 仅能为白名单内的 R0 只读目标生成
最小恢复计划：页面观察/提取、收藏夹列出/检查/预览、官方下载来源发现，或标签页/窗口
元数据。购物、写入、表单和外部副作用绝不走这条恢复路径。

## 浏览器掌控的保证

- 每个普通 Profile 一份服务，其桌面主无痕 Profile 使用另一份独立服务；Guest、System 和
  辅助 OTR Profile 不启动 Agent。
- 工具注册表在编译期固定；模型不能创建工具，也不能执行任意 JavaScript、shell、通用
  CDP 或本地文件访问。
- 精确绑定 tab、origin 和文档。导航会让旧观察和旧动作引用失效。
- 密码、Cookie、OTP、支付信息、受保护表单值和 API key 不进入模型上下文、任务存储或
  构建产物。Aegis Actor journal、诊断和 trace 会抑制私密数据；默认 NetLog 采集会脱敏
  `x-api-key` 与 `x-goog-api-key`。显式使用 `kIncludeSensitive` 的 NetLog 仍沿用 Chromium
  的敏感数据语义，可能包含秘密。
- 普通 Profile 的模型凭据由浏览器凭据机制保存，并按 endpoint 隔离；无痕凭据只存在于
  会话内存。loopback 可使用 HTTP，远端模型 endpoint 必须使用支持的 HTTPS。
- R0 只读动作可在任务确认范围内执行；R1 可逆动作保持有界；R2 写入或外部副作用需要
  精确 action 审批；R3 结账、付款和最终提交必须用户接管。
- 是否完成由浏览器后置条件决定，不采信模型自然语言声明。

## 桌面无痕隔离

桌面主无痕服务独立持有 Agent Runtime、当前页摘要、`chrome://aegis` 控制面、任务状态、
Actor 和隐私事件。路由严格使用实际所属 Profile；无痕服务不会退回普通服务，也不会写入
普通 Profile。

无痕 TaskStore、模型凭据、自动化状态、撤销凭证、高级下载所有权、事件历史和已学习的
CNAME 别名都只存在于内存，会随无痕会话结束而清除。历史搜索只读取该无痕会话内的导航
记录。Actor 日志、诊断日志和 trace 会隐藏私密 URL、页面/任务数据、目标和凭据标识；
无痕登录质量记录不会上传，无痕监控也不会发送系统通知。

用户明确批准的收藏夹修改和已完成下载是例外：它们保留 Chromium 原生、用户可见的持久
语义，可能在无痕窗口关闭后继续存在。关闭无痕会话会取消仍在进行的 Agent 下载和种子
传输，撤销任务控制权，并保留已经写入的种子字节。种子所有权只在同一 Profile 会话内跨
设置页刷新保留，进入终态后释放，且绝不跨 Profile。

进程级 CDP 无法按 Profile 隔离调试端点可见目标，因此创建任一主无痕会话会立即停止并
阻断整个进程的所有 HTTP 与 pipe 远程调试传输，包括并非由 Aegis 启动的传输。最后一个
无痕窗口关闭后它仍保持关闭，只能由用户在普通 Profile 中明确重新启用。每个普通 Profile
都在初始化时安装守卫，早于其首个 Browser 或 renderer。这是有意保留的安全边界，不会
停用原生、绑定文档的 Agent。

Guest、System 和辅助 OTR Profile 不接收 Aegis 界面/服务，也不安装其网络 throttle、指纹
保护或过滤列表配置。普通与主无痕 Profile 使用不透明且不同的网络分区标识，已学习的
CNAME 别名不会跨 Profile，并在 Profile 关闭时移除。

## 用户界面

桌面端普通与主无痕 Profile 都使用明显的固定 Agent 按钮和侧栏。Android 使用明显的
浏览器入口、常用目标底部面板和完整 Agent 任务页。两端共享目标模型、任务时间线、
provider/model 状态、易懂的恢复提示和常用场景：

- 总结当前页面；
- 对比商品；
- 预览后整理收藏夹，并支持撤销；
- 检查收藏夹 URL；
- 查找安全的官方下载；
- 研究主题或用户点名的网站。

自动化从“高级设置”中独立出来。预设包括降价、到货、网页变化和 URL 有效性，支持
每 15 分钟、每小时、每 6 小时、每天或每周。自动化只在浏览器可运行时调度，使用有界
重试和退避，并可暂停或删除。

## P0–P4 原型比较

| 原型 | 形态 | 优点 | 阻断问题 | 结论 |
|---|---|---|---|---|
| P0 | 只做提示词聊天/搜索 | 最快形成界面 | 把所有需求当文本或搜索，没有可信执行循环 | 淘汰 |
| P1 | 扩展/CDP 外部 Agent | 迭代快 | 权限过宽，Profile/文档生命周期弱，产品融合差 | 仅研究 |
| P2 | WebMCP/纯 DOM Agent | 页面工具结构化 | 无法完整管理原生收藏夹、下载、标签页、隐私和反钓鱼状态 | 只作为组件 |
| P3 | 纯 Chromium Actor Agent | 页面动作绑定强 | 单独无法覆盖浏览器原生数据和生命周期 | 只作为组件 |
| P4 | 原生混合 Runtime | 在同一策略/验证器下组合模型、Actor 与浏览器原生工具 | 集成与跨平台测试成本最高 | **选用** |

P4 是满足“理解、规划、执行、观察、验证”的最小完整设计，同时不会把模型变成高权限的
远程浏览器控制器。

## 平台与验收边界

macOS、Windows 和 Android 必须从同一候选源码构建，并记录产物哈希。Android 必须安装
到指定 Pixel 真机；Windows 必须在指定 Windows 主机上构建并实际操作。iOS 明确不在
本轮 v2 实施范围内。

验收必须真实检查：入口可发现、不预先打开页面的任务、模型规划与一次有界修复、页面摘要、
点名站点路由、收藏夹、下载、定时任务、隐私保护、反钓鱼、新手可读错误、普通/无痕隔离、
凭据/浏览数据不泄漏，以及精确源码/产物身份。只有源码构建或单元测试通过，不能代替跨平台
产品验收。
