## Actions architecture and repository admission

Use iOS-specific workflow names and a per-repository iOS activation variable (AEGIS_IOS_RELEASE_ENABLED), not a shared all-platform release switch. Naming may be refined by the builder, but keep the following responsibilities separate:

- ios-release-validation: credential-free contracts and unsigned native compilation on iOS release branches/PRs. No signing/ASC secrets. Preserve the existing repository quality checks and run relevant Ruby/Python/Node regressions and actionlint.
- ios-release: manual/reusable signing package plus artifact output, optionally private GitHub Draft. Signing material only in the protected package job. A candidate/ios/<version>-<profile>.<build> push invokes this via an iOS-only candidate-tag wrapper. Candidate Draft always remains draft/prerelease, with no published_at, exact tag/source and asset digests verified.
- ios-testflight: explicit store stages using a previously completed package artifact run and, for post-upload mutations, its completed upload receipt. Do not rebuild/reupload just to distribute or edit metadata. Check original run/workflow/repository/attempt, exact source SHA/tree, manifest hash, profile/version/build and stage receipt before use. Untrusted or wrong-source artifacts are rejected. Status/readback never mutate the store. ASC secrets appear only in protected store jobs; Draft alone receives contents:write.

Upstream admission requires exact repository ID, exact current main SHA and latest terminal successful quality/quality-gate checks for that SHA. Candidate tags must point to that exact main. Repeat source/ref checks immediately before a mutation. Fork testing is explicitly opt-in, verifies configured fork ID and upstream parent, and requires latest terminal successful exact-source credential-free iOS validation. No wildcard source, permissive fallback or replay of an older passing attempt.

Existing source-bound receipts stay bound after merge: the fork-tested SHA does not qualify a different merged main SHA. Follow PR/head/merge-candidate checks as applicable, merge only after required checks and added iOS gates pass, then follow fresh main CI before activation and upstream delivery.

## Signing and runner approach

Retain the installed Apple Distribution key and existing three App Store profiles on this host. Do not export a private signing key or change shared keychain ACL/search-list/timeout, shared proxy, VM, runner service, or SSD-root permissions. Use task-owned ephemeral iOS signing runners with distinct platform/repository labels and narrow protected environment source rules. A reusable runner helper may prepare/register one ephemeral runner for one verified queued signing job, verify complete runner payload and signing preconditions before registration, keep tokens in memory/environment only, and unregister only its own runner. Missing startup templates must fail before credentials/registration (regression for the observed local operational failure). Unknown registration/job outcome must be reconciled rather than duplicated.

Use official runner payload/checksum or a verified existing owned payload. Work, logs and bundle caches remain task-owned. Disk admission and observation preserve at least 8 GiB genuinely free internally and 15 GiB externally. Sensitive data never appears in logs, public evidence or argv. Signing material names use type-only names such as Distribution.cer and AppStore.mobileprovision, without dates or beta labels.
