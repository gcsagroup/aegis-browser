# 更新元数据与恢复设计（U04）

当前浏览器已有 GitHub Release 发现、平台选择、大小与 SHA-256 校验、文件暂存及“打开下载位置”流程。它没有自动安装器，下载成功不能显示为已安装。新增离线原型仅验证元数据设计及负例，尚未接入产品，不改变现有网络请求。

## 第一版协议

元数据外层只有 `payload` 和 Base64 编码的 `signature`；签名覆盖 `payload` 的原始 UTF-8 字节。使用 Ed25519，公钥由客户端独立提供，不能从同一下载响应接受新的信任根。载荷是紧凑 JSON，包含：协议版本、四段产品版本、递增序号、发布时间、到期时间、平台、固定仓库下载地址、SHA-256 和字节大小。

原型限制元数据 16 KiB、包 2 GiB、有效期最长 7 天；这些是本地设计预算，需要在真实发行包与更新频率确定后复核。版本数字逐段比较，不作字符串排序；当前包不需要重新安装，低版本拒绝。只有固定 GitHub 仓库的对应版本地址可作为初始下载地址，重定向仍须经过现有原生下载白名单。

客户端保留“最高已接受序号＋该载荷摘要”，拒绝旧序号及相同序号的不同内容。调用方必须提供可信当前时间；没有时钟就不能将到期检查标为成功。首次使用没有历史序号，无法仅靠递增序号排除所有旧但未到期的合法元数据；应在包内预置最低序号与信任根，后续连同签名版本维护。

下载后重新验证元数据签名、期限、平台和版本，再验证实际文件大小与摘要。不能接受调用方自报的 `verified=true` 作为前置证明。原型不会把元数据签名或文件摘要通过转换为平台代码签名通过，更不会转换为安装成功。

## 产品接入顺序

1. 发行侧确定长期公钥、密钥保管和签名流程；验证发行包体积及平台命名。没有这些条件时保留“元数据签名未核验”，不能用测试密钥上线。
2. 将验证逻辑迁移到原生更新链路，独立核验 Apple 代码签名、包身份、团队标识和版本。验证前不启动安装包。
3. 最高序号只在元数据完整验证后原子持久化，避免检查中断破坏状态；签名根轮换需要单独设计，不能从网络错误回退为信任任意新密钥。
4. 只有实际安装并重新读取固定 App 的版本与签名后才能显示“已安装”。现阶段保留用户手动安装；浏览器中不增加伪安装进度。

## 本地恢复流程

固定测试 App 更新前保存旧包及独立资料副本。新包在暂存位置做大小、摘要、签名、版本检查，退出测试 App 后再替换固定路径。启动失败时保留新包、日志与新资料；恢复旧包前核对资料格式兼容性，不能让旧程序直接打开可能升级过的数据库。若需要恢复资料副本，先保留新资料并明确新任务数据损失范围。

公开发行、公证申请、生产密钥与在线安装链路不在当前本地实施授权中。本设计不声称已经具备 TUF 的完整密钥轮换、阈值签名或抗冻结能力。

## 已执行的负例

```bash
node --test apps/browser/scripts/update-metadata-prototype_test.mjs
```

14 项测试通过：合法签名与文件、过期、未来发布、有效期越界、错误平台、产品降级、歧义版本、非法摘要与大小、其他仓库、旧版本链接、额外字段、篡改签名、未知公钥、元数据回滚、同序号内容变化、损坏/截断包、伪造“已验证”标志、重复 JSON 字段和缺失时钟。部分负例在同一测试项中执行。

测试密钥只存在于 Node 进程内，不写入文件。相关模块为 `apps/browser/scripts/update-metadata-prototype.mjs`。浏览器原生接入、真实平台签名、断网下载和安装失败恢复仍待验收；U04 尚未通过。
